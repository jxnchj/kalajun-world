# 林溪原生连续绘制段 GPU 定位（49，2026-10-28）

本轮确认：当前正式入口的中距照片树冠确实是主要 GPU 工作之一。主颜色中的一个连续段为 **13.217ms**，反射中的完整 mode1 连续段为 **7.889ms**。这不是整 pass 时间，也不是已经取得的性能收益。没有启用或接入任何新的生产优化。

**后续环境纠正：本轮不具备独占GPU条件。** 主线确认保留的旧场景tab1839973780在另一个Chrome窗口活跃时仍一直visible，98.796秒内renderer帧计数增加3112，5分钟没有hidden事件。本轮仅确认自己session临时页关闭，不足以证明其他会话没有运行场景。因此这里约110ms的RAF值不得再称单世界帧率，13.217/7.889ms等query也属于存在其他场景GPU争用时的单段读数，不能据此精确预测独占成本或收益。原draw/三角/实例数量、顺序签名和恢复结果仍有效，实际重照片冠的提交规模仍有来源证据。

主线已真实关闭旧3780与旧3777；唯一正式49页面同条件60稳定+180RAF的新基线为均值40.093ms、p95 50.1ms（`default49-single-world-baseline.json`），pose未变、q0、errors为空。环境收拢不是代码优化成果。后续高冠候选必须在唯一3D页同构建A/B/B/A复验，不与本轮约110ms相减。

证据：`docs/previews/v2-route-craft-38/gpu-runs49-forest.json`。诊断源码为 `web/src/v2/gpu-draw-runs49.js`，未被默认入口导入，不改主构建；它在已加载的正式页面显式导入并于结束恢复。

## 条件与方法

- Chrome，桌面横屏，1280×800，实际 renderer DPR1；正式 `/dist-v2/v2.html?view=river-forest&time=870&debug=1`，没有 profile 或实验开关。
- 原林溪位置 `[-3611.851169467755,2329.157270885741,4805.483400316967]`，yaw `-29.88794104541604`，pitch `-10`；q0/m0 后稳定60 RAF。保持正常 RAF、真实风与所有原系统，不使用 review hold。
- 先60 RAF仅记录时间戳；再8 RAF记录原始连续绘制目录；随后60 RAF轮换12个目录中最大的树冠段，每 RAF **最多一个** `TIME_ELAPSED_EXT` query，pending上限8。最后恢复全部hook，再记录60 RAF。
- 原 `renderBufferDirect` 原参数、顺序、矩阵、几何、材质和实例数量完全直通；clear、render-target与shadow边界结束当前段，不把互不连续工作拼成一个query。原有多段密集query曾明显放大阴影成本（见 `shadow-static39-isolation.md`），因此本轮不采用那种方法。
- 48个query均有效，0 disjoint、0 foreign-owner、0容量拒绝、0错误、pending最终0。68帧中的 `discarded=20` 是8个无query目录帧加12个目标段当帧未出现，不是20次GPU执行失败。反射/阴影按原调度刷新，不强制重画来凑样本。
- 每个实测段的原draw数、三角数、按顺序的 `(object, geometry, material, start, end, instances)` 哈希均与无query目录相同；`baselineSame` 为48/48。这里没有新做冻结逐像素对照，不能把绘制透明诊断说成新的美术验收。

## 下一项是否已有足够实施依据

**足以确定热点，不足以直接选择一个净收益已可信的生产改动。** mode1中距照片树冠应优先于再改一项约1ms的CPU wrapper，但本轮测到的是实际提交成本，没有证明其中哪些完整叶片或三角无贡献。

已有证据必须保留：

- `tree-view42-browser.md` / `tree-view-pass-share42-browser.md` / `tree-wind-atlas44-browser.md`：逐视图整根裁剪确实省约4ms GPU，但CPU与整体RAF恶化；不能重新包装复活。
- `photo-cluster-audit42.md`：枝簇粒度比整根仅额外省主画面3.27–3.77%的照片三角，却可能让52 draw变359/715；不实现。
- `docs/previews/v2-route-craft-28/batch-size-timings.json`：旧全树64m两轮74.06/76.77ms，96m为67.29/69.06ms；64m虽然GPU35.96ms低于96m约37.23ms，整体更慢。不能把恢复全树64m称为新方向。
- 已有透明边界修剪、完整属性索引与共面合并已执行；本次没有发现新的可证明恒零三角。不能删内冠/叶片、缩减根数、简化风、降反射/阴影质量换帧率。

范围最小、尚未被上述实验直接测过的候选，仅是**重树冠的固定原生空间分组**：mode1/5照片材质可细分，低成本树干/内核仍96m；所有pass继续使用原生InstancedMesh，只有原membership变化才更新矩阵，没有逐pass复制或新shader。现源码的根风缓存按root.id复用，不会因为多分组重算同根风，但照片组与树干组分离会增加风VBO上传/分配；更多原生draw及alpha深度排序也是明确代价。

因此目前只列为待核算假设，**没有修改生态源码，也没有创建此运行时候选**。最小下一证据是对当前完整根/包络，在原主视图、反射、3级CSM下只读计算96m与照片单独较细分组的实际draw/提交三角/风buffer字节；必须同时保留原根、几何和完整风包络，并与旧64m结果区分。若收益只重复已否决整根机会、draw或上传代价抵消，便终止；即使计数有利，也只有独立候选的真实全RAF对照才可决定是否采用。

# 喀拉峻世界重构方案

版本 1.0 · 2026 年 10 月 19 日

本方案用于重构位于 `.` 的 Three.js 世界。目标是建立一个具有喀拉峻与琼库什台地方辨识度、融合不同时期美好元素、可连续探索的艺术化现实场景。它保留草原的辽阔与牧居生活感，拥有可信的地貌、精细的室内外环境、自然的动态和富有童话气氛的光色。

采用系统性重构：继续使用 Three.js，重新组织世界数据、材质光照、连续分级、植被运动、分区加载及角色物理；现有资料、模型和代码逐项验证后复用。最终交付覆盖约定的整个世界，代表样区用于验证方法与质量标准。

当前交付是设计与实施方案。下文的阶段、模块、性能目标和目录均为拟实施内容；代码检查已确认的问题与尚待实测的判断分别说明。

## 1 世界设定与决策原则

### 1.1 地方身份与时间选择

世界不绑定某个年份。真实地理骨架、历史人文布局、选中的现代建筑和艺术设计共同构成最终场景。

| 层次 | 保持或选择的内容 | 判断依据 |
| --- | --- | --- |
| 地理骨架 | 山脊、河谷、坡向、水系、主要森林格局、代表性眺望关系 | 地理资料与多方向实景能相互支持，熟悉当地的人能辨认 |
| 人文布局 | 较疏朗的历史聚落、牧道、围栏、毡房、牧场及选中的民宿 | 空间合理，保留开阔感与生活气息，不因新资料出现就自动增加开发设施 |
| 艺术设计 | 色彩、天气、局部构图、植物形态、缺资料空间的完整设计 | 增强美感，同时遵守尺度、生态、建筑功能与光照关系 |

项目记录提到 2013 年布局及 2022 年影像，用户对年份的记忆是约数。实施时核对源文件和影像元数据；准确年份用于理解来源，不成为强制复刻日期。最终只维护一份经过取舍的世界布局，不能把各年代所有对象直接叠加。

新资料用于补足认识。当前照片可以帮助制作选中的民宿、家具和材料，但不会自动覆盖原有疏朗布局。艺术调整山体时保留真实海拔字段，避免“抬高远山”意外改变雪线、植被和岩地分类。

### 1.2 美术方向

建议以富有生机的草甸季节作为第一版统一季相，具体花期、草色和积雪关系在资料整理阶段确定。暂不同时制作四季，以免在世界尚未统一时扩大变量。

画面以起伏草坡和开阔天空为主体。深色云杉与河谷形成空间层次，远山通过地形、光照和空气透视产生纵深；木屋、毡房、牧道与围栏提供生活尺度。花丛在适合的生境或村舍附近形成重点，保留大面积开阔草甸，区分野生群落与庭院栽培。

童话感主要由构图、色彩节奏、优美轮廓、天气和光线产生。保留木材、布料、岩石、土壤与水的材质差异，避免全世界套用相同亮部、统一塑料反光或过强泛光。

### 1.3 工作优先级

优先修复影响全世界的结构和表现问题，再完成各类区域的共同质量，随后雕琢重点细节。

单件资产达到所在场景的观察距离、形体、材质、运动和功能标准后，结束本轮细化并推广。只有整体验证暴露的问题才重新打开它。判断新增细节的依据是它是否改善地方辨识度、空间可信度或实际探索体验。

## 2 重构范围与现有基础的处理

沿用现有核心约 20.48 公里、远景约 81.92 公里的范围作为初始工作边界。阶段 0 明确可步行、可飞行、可进入建筑的实际范围；不能以一个精细样区替代原有大世界，也不能把原来可达的区域悄悄变成背景。

| 现有内容 | 处理决定 | 原因与验证重点 |
| --- | --- | --- |
| 原始高程、地类、历史布局、照片与校准工具 | 保留为资料基础，重新核对重要空间关系 | 有数据来源不等于全部处理、摆放和艺术改动正确 |
| 地形四叉树与高度查询 | 复用思路，重整数据接口和连续分级 | 分离地理海拔、最终场景地形与观看距离相关的显示细节 |
| 建筑、植物、动物的 Blender 脚本 | 作为制作工具继续使用，增加可编辑主工程 | 避免重跑脚本覆盖已经完成的艺术调整 |
| GLB 和纹理 | 按形体、材质及使用场景筛选 | 一些资产已有足够几何，主要缺材质输入或合理受光 |
| 卡通受光、逐材质亮度补偿、现有后期链 | 重构核心，逐步撤除临时补偿 | 当前有高光截断和多处增益，单独调整曝光无法统一修复 |
| 近中远植物与森林 | 重构表示和交接，保留可用生态数据 | 不能在切换距离改变位置、株数、主要轮廓和运动状态 |
| 角色输入、动画、对象交互意图 | 保留可用行为，接入新运动与碰撞层 | 门、台阶、地面、相机必须遵守一致的空间规则 |
| 自制终点推离碰撞 | 由成熟角色控制与形状查询替代核心职责 | 解决快速移动、落地、顶头、转角及相机穿透的结构缺口 |
| 启动时图卡捕获、静态统计、碰撞生成 | 尽量移至资产构建阶段 | 浏览器优先读取可用结果，减少首屏等待与移动长帧 |
| 旧截图与历史测试记录 | 用于回归对照 | 不作为新版本已通过验收的证明 |

第一轮不以换框架、全面改 TypeScript 或引入通用 ECS 为前置工作。保留 Vite、现有 JavaScript 工程和已安装的 Three.js 基线；依赖升级与渲染重构分开，遇到明确需求再变更。

## 3 整体架构

世界分为制作数据、离线构建和浏览器运行三层。资产位置和世界状态有唯一来源，Blender 与 Three.js 都从这份数据读取。

制作关系为：

**地理与实景资料 → 世界布局与艺术选择 → Blender 主工程及地形制作工具 → 资产构建产物 → Three.js 连续世界**

| 层或模块 | 职责 | 对其他模块提供什么 |
| --- | --- | --- |
| WorldData | 坐标、地形、生态、经过选择的聚落与对象布局、来源和艺术调整 | 稳定对象 ID、空间范围、原型、位置、尺度、功能 |
| AssetBuild | 导出、烘焙、减面、纹理压缩、碰撞处理、图卡和清单生成 | 可重建、版本明确的运行资产 |
| WorldRuntime | 世界坐标、分区生命周期、时间、对象状态、加载优先级 | 一个统一的世界状态及更新顺序 |
| TerrainSystem | 地形查询、可见网格、边界衔接、地表材质和河床 | 同源的渲染与碰撞地表，稳定的生态分类数据 |
| EnvironmentSystem | 太阳、天空、云、空气、风和天气状态 | 所有材质、植物、水、阴影共同使用的环境参数 |
| RenderSystem | 物理材质、阴影、环境照明、反射、曝光、后期 | 一致的室内外画面，明确的资源与通道成本 |
| EcologySystem | 群落分布、植物身份、近景运动和多级表示 | 不随相机位置重新生成的地物及共享风动结果 |
| SettlementSystem | 建筑外壳、房间、家具、门窗、灯光和场地连接 | 完整建筑实例、室内加载范围及交互连接点 |
| PhysicsSystem | 角色、相机、静态地物、动态门和动物的空间约束 | 地面、障碍、触发区及运动查询 |
| ExperienceSystem | 输入、漫游、角色切换、已有互动与观景功能 | 可连续探索的使用路径 |
| Diagnostics | 帧时间、内存、加载、分区及关键状态检查 | 开发验证数据；不把实现细节放进正常游玩界面 |

依赖方向保持清晰：世界数据决定对象，环境状态驱动表现，物理和渲染读取相同空间定义。不能让某个材质反过来偷偷决定生态种类，不能让不同 LOD 自己重新生成另一批树。

固定步长更新物理；渲染按实际帧率插值。门和动物的位置先更新到统一状态，再同步碰撞、渲染及相机查询，避免一帧内看见的物体与撞到的位置不同。

### 3.1 坐标与大范围精度

制作数据继续使用地理坐标及米制局部坐标，轴向转换只在明确的导入导出边界发生。建筑主工程以局部原点制作，世界位置单独保存。

CPU 保留足够精度的世界坐标；渲染和近场物理使用相机附近的局部原点。跨区域调整原点时，门状态、风采样、对象 ID 和分区索引不改变。地球曲率等远景表达若保留，地面、建筑与树必须一致，不能各自弯曲。

### 3.2 建议目录职责

以下是拟定的逻辑分工，不要求在第一天移动全部旧文件：

| 目录 | 内容 |
| --- | --- |
| `data/world/` | 统一世界清单、来源记录、生态区和选定布局 |
| `assets/source/` | 新制作的 Blender 主工程与源纹理；旧源文件先原位保留 |
| `tools/blender/` | 现有及新增建模、场地装配与导出脚本 |
| `tools/build/` | 资产校验、压缩、分区打包、图卡与元数据生成 |
| `web/public/world-v2/` | 新的运行时资产，避免覆盖现有资产 |
| `web/src/world/` | 世界状态、坐标、分区与加载 |
| `web/src/render/` | 材质、环境、阴影、水和后期 |
| `web/src/ecology/` | 植被分布、风响应和细节分级 |
| `web/src/physics/` | 角色控制、碰撞、相机查询 |
| `web/src/settlements/` | 建筑外壳、室内和门窗灯具 |
| `docs/` | 本方案、必要的参考整理与实际验收结果 |

每个新模块先通过薄适配层接入现有入口；整体通过前保持旧入口可运行。目录整理不能代替功能交付。

## 4 地形与整体景观

### 4.1 重新核对地理骨架

使用原始高程、可取得的独立地理资料、带方向和位置线索的地面照片及历史影像，对全域主要山脊、谷底、水流方向、坡向和聚落位置进行交叉检查。覆盖多个方位和距离，避免只围绕营地拟合一张照片。

核对坐标系统、GCJ-02 与 WGS-84 转换、垂直基准、采样方向及插值范围。原始约 30 米数据插成 10 米网格不能增加测量信息；近景补出的土包和冲沟属于设计细节。

优先修正影响天际线、河流流向、建筑落地和主要路径的错误。对缺乏精细资料的坡坎，可以基于地貌逻辑与照片塑形，标记为设计补全，不假称测绘复原。

### 4.2 三种高度各司其职

- 地理高程保留真实来源，服务于生态、海拔与地貌推理。
- 场景地形包括选定的道路切坡、台地、河床和合理艺术塑形，成为行走、建筑落地与碰撞的共同地表。
- 显示细节包含远处可以简化的微地形、法线和纹理频率，不应改变实际空间与生态种类。

艺术抬山若采用，应是可解释、空间连续的世界设计；不能随相机靠近消失。地表类型依赖稳定地理数据和明确编辑层，不能直接从随 LOD 变化的着色法线重新推导。

### 4.3 连续的远近表现

由同源高程生成多级数据，处理好相邻层级的边界、法线与轮廓。采用屏幕误差选择细节，增加切换迟滞，避免在阈值附近反复跳变。

草甸、林地、岩地和水岸各级表示共享颜色分布与覆盖统计。远处可以减少单叶、细枝和碎石，山脊、林缘、屋顶、河岸等主要轮廓保持稳定。不能用增厚远草、缩小树高或加浓雾掩盖层级不一致。

各区域应有明确性格：开阔高坡、林缘草甸、谷地湿润带、溪岸、岩坡和牧居区相互过渡。具体分区由资料与场地判断确定，不预先机械套用同一配方。

## 5 渲染与环境

### 5.1 技术默认选择

继续采用 Three.js 的 WebGLRenderer，先完成统一的 PBR 材质与环境架构。WebGPU 不列为第一轮前置条件；只有目标设备和实测瓶颈表明迁移有明确收益时，再单独评估兼容性与改造量。

普通木材、石头、布料、金属采用标准物理材质或受控扩展；植被保留专用薄片透光与风形变，地形和水使用专门材质，但共享照明、阴影、雾与输出规范。

Three.js 的标准材质已有金属粗糙度工作流及环境照明支持。这里的工作是正确保留资产输入、统一环境和艺术控制，并非单纯打开一个 PBR 开关。[官方材质说明](https://threejs.org/docs/pages/MeshStandardMaterial.html)

### 5.2 统一颜色与光照链路

底色纹理进入线性计算；法线、粗糙度等数据纹理按非颜色数据处理。保留 HDR 中的光照差异，经过统一曝光和色调映射，再做适度显示调色。

逐步撤除材质内部为特定机位加入的高光截断、色调映射后增益和反向补偿。艺术参数集中管理，避免某间房、某片草各自拥有一套亮度修复。

第一组校准覆盖白色布料、深浅木材、石头、草叶和水面，先在高太阳条件恢复形体和纹理，再处理金色时段、阴天及夜间。正午按太阳高度判断，不能把北京时间 12 点直接当作当地太阳正午。

### 5.3 太阳 天空 云与阴影

保留可用的真实太阳方位计算。太阳直射、天空环境照明、雾和云共用时刻与天气状态；环境反射根据变化分时更新或平滑过渡，不为每帧重建完整环境增加无谓成本。

近中景以标准材质可接入的级联阴影为默认路线，远山保留经过校核的高度场遮蔽；重新校准范围、接触感、偏移和稳定性。通过共用顶点变换适配，让植被在主画面与阴影通道使用一致的形变。山体遮蔽主要约束太阳直射，避免把所有天空与间接照明一起乘暗。

第一版云采用有空间层次的轻量表现与对应云影，优先保证移动、光向和地面明暗变化一致。完整高成本体积云不作为基础画质成立的前提。林间光束由遮挡和散射条件控制，不能从全屏亮物体任意拉出光柱。

### 5.4 室内照明

建筑具有完整墙体、屋顶厚度和门窗开口。室内环境照明应体现天空可见度与空间遮挡，不能直接沿用无遮挡室外环境亮度。

离线烘焙用于稳定的几何遮蔽、天空可见度，以及可单独控制的固定灯光间接贡献；变化的太阳阴影不烘进底色。默认使用少量关键时段的室内间接光数据与房间局部环境探针，平滑衔接昼夜；固定灯具的间接贡献单独控制。动态人物通过局部间接光采样获得一致受光，门窗变化的实时直射和遮挡单独更新。先在代表房间验证这种近似的适用范围，避免把探针当作自动完成全局光照。

灯具的可见发光面与照亮周围的光源分别定义。近处少量灯提供真实局部受光，远处使用匹配的低成本表示。门口与窗边的曝光变化连续且受限，不能靠大幅提亮室内导致窗外全白。

### 5.5 水体

保留合理河道资料，重做近景河床、岸线和水面表达。深浅以水面到实际河床的距离或一致的深度场为依据，体现吸收、折射、湿润石头及岸边透明层次。

环境反射作为基础；重点近景、近似平面的水段增加受限范围的场景反射。陡坡、弯折或不同水位的溪段分开处理，不能对整条山溪套一个无限平面反射。反射范围和更新频率由画面贡献决定。

水流方向、速度和波纹由河段流向、坡度与障碍分布驱动；石头接触泡沫使用真实障碍或离线接触数据，不能只在河道边缘随机贴白色。第一版采用视觉可信的实时近似，不承诺科学流体模拟。远处简化时保持水位、河宽、岸线和主要反光关系。

## 6 植被与自然动态

### 6.1 共同分布与稳定身份

植物分布来自坡向、海拔、湿度、土壤、林冠和人类活动共同定义的生态规则。使用世界坐标和稳定种子生成植株或草簇 ID；只有近景活动范围保存较完整运动状态，不为全域逐叶常驻分配模拟内存。

同一株树、花或草簇在各级表示中共享根点、尺度、形态参数和主要朝向。远处允许用聚合表示，但覆盖率、林缘轮廓和色彩分布来自同一群落，不能另撒一批植物。

图卡和多视角替身从最终同源资产生成。选择距离参考屏幕尺寸、轮廓与视差误差，重要近景支持侧看、俯视和绕行。转换保持运动主相位及整体姿态，不重置弹簧、不突然改变株数。

### 6.2 风与物体响应分离

公共风场提供方向、速度、阵风和空间变化，植物根据自身结构响应。局部林冠或建筑遮挡可以降低风力，不能让所有室内外对象同时同幅度摆动。

| 对象 | 近景运动结构 | 中远景简化要求 |
| --- | --- | --- |
| 花 | 茎、花梗与花头耦合；考虑重力、刚度、受风面积、惯性与阻尼 | 保持主要倾角、花头滞后和阵风相位 |
| 草 | 根部约束，沿叶片变化的柔性曲线，叶尖回弹与少量扭转 | 保持草浪方向、群落节奏与平均弯曲 |
| 灌木 | 主枝较稳、细枝较活跃、叶片有微动 | 保留主要枝冠节奏 |
| 云杉 | 主干稳定、枝层分级响应，细枝针叶轻动 | 保持树冠轮廓与低频响应 |

近景运动不以增加随机噪声代替物理关系。以定风、阵风、停风回弹和角色拨动作为校准条件；查看姿态和阴影是否一起运动。

### 6.3 动物与人物

复用已有效的角色输入、切换、骨架动画和动物资产，统一尺度、脚部落地、阴影及碰撞。先让既有行为可靠，再补充能改善牧居生活感的行为；不在环境重构期间扩展成新的复杂游戏系统。

## 7 Blender 与 Three.js 的分工

| 工作 | Blender 与离线工具 | Three.js 运行时 |
| --- | --- | --- |
| 全域地形 | GIS 处理多级高程与地类；Blender 处理必要的局部坡坎和场地 | 分区加载、连续 LOD、地形显示和高度查询 |
| 建筑与室内 | 完整建模、空间组织、家具、门窗、UV、材质、碰撞和连接点 | 场地装配、房间加载、开门、照明、角色与相机交互 |
| 花草树木 | 形体、枝叶关系、法线、透光参数、风权重与同源 LOD | 分布、实例化、公共风场、近景动力与分级交接 |
| 水岸 | 河床、石头、岸线与障碍数据 | 水面、流动、反射、折射、深度与泡沫 |
| 光照 | 材质校准、稳定遮蔽及可用的间接光数据 | 太阳、天气、实时阴影、局部灯光、环境照明与曝光 |
| 动画 | 骨架、权重、动作及门轴等局部结构 | 状态、混合、事件及物理同步 |
| 优化 | 减面、图卡、纹理处理、压缩与资产元数据 | 可见性、预取、资源释放、运行质量调度 |

不把整个世界做成一个巨大 GLB。Blender 中建立轻量场地装配工程，读取共同世界位置和地形裁片，以便检查建筑、坡面与道路的关系；运行时仍按资产和空间分区组织。

Blender 预览灯光不会自动变成网页里的同样效果。每类资产必须在真实 Three.js 环境中完成外观检查，离线渲染图不能替代浏览器验收。

## 8 资产制作流程与数据约定

### 8.1 制作顺序

1. **定位与参考。** 确定对象属于哪个区域、时期选择和观察距离，收集整体、侧面、细部及必要室内资料。
2. **空间初稿。** 在真实尺度下制作轮廓和基本空间，放回世界检查山坡、道路、入口、窗景与附近对象的关系。
3. **可编辑主工程。** 在 Blender 保存模型、材质、UV、变体、碰撞及连接点；区分脚本生成部分与艺术调整，防止重复生成覆盖成品。
4. **材质与结构。** 制作中性的底色、粗糙度、法线等输入，补充影响近看与轮廓的几何；共享木材、布料、石头等材料族。
5. **动态与功能。** 添加风权重、支点、骨架、门轴、可走表面、简化碰撞和灯具定义。
6. **分级派生。** 从同源资产制作 LOD、必要的多视角替身及包围体，检查轮廓、平均色、透光和运动交接。
7. **导出与处理。** 输出 GLB、纹理、资产清单与附属数据；再进行网格压缩和 KTX2 纹理处理。
8. **浏览器回看。** 在统一环境与实际所在区域验证尺度、受光、阴影、透明、碰撞、分级和加载。
9. **推广。** 达到类别标准后形成变体，覆盖其他区域；完整保留源工程，以便共享问题统一修复。

AI 可以辅助参考整理、Blender Python、基础形体与纹理候选。生成结果必须经过尺度、结构、材质和场景检查；图像生成不能直接推断出可靠的多视角建筑或完整拓扑。现有素材、程序制作、人工调整及必要的外部资产可组合使用，技术选择服务于最终效果。

### 8.2 最小资产约定

| 项目 | 约定 |
| --- | --- |
| 身份 | 稳定 `assetId` 与版本，实例另有 `entityId`；LOD 不改变对象身份 |
| 尺度 | 米制、明确局部原点与轴向，导出后无意外负缩放或尺寸变化 |
| 材质 | 明确底色、法线、粗糙度、金属度、AO、发光、透明或薄片透光；规定色彩空间和纹理通道 |
| 几何 | 真实轮廓、必要厚度、正确法线；双面材质不用于掩盖所有缺面问题 |
| 分级 | 同源、同尺度、同支点；规定主要轮廓与颜色匹配，不能缩入地下替代切换 |
| 动态 | 风权重、关节与支点、动画名、门轴和灯具挂点有明确含义 |
| 碰撞 | 静态简化网格或组合形状；动态对象使用合适的凸体或基本形状 |
| 元数据 | 包围体、用途、参考来源、时期选择、依赖与估计资源量 |
| 加载 | 外壳、室内和远景资产可分别加载；资源依赖可去重与释放 |

Blender 的常见 PBR 参数通过 glTF 导出，特殊风权重、碰撞和行为通过明确的自定义属性或附属清单传递。不能依赖任意 Blender 节点自动在网页工作。

现有顶点色混用了 AO 与天空可见度，迁移时明确拆分或重新导出，不能直接当普通 RGB 顶点颜色乘到 PBR 底色。现有木材贴图中的固定高光也需评估，避免在动态光照下重复受光。

网格默认评估 Meshopt，纹理使用 KTX2/Basis 路线；先验证无压缩版本，再检查法线、花瓣透明边缘和颜色是否损坏。Three.js 的 GLTFLoader 和 KTX2Loader 提供相应运行接入能力，导出构建仍需配置。[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)、[KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)

### 8.3 资料如何使用

每条关键参考记录来源、时期、对象、可确认内容及“观察／推断／设计”。宣传照片用于形态和材料，游客照片补充侧面与使用状态；广角透视、滤镜和装修年份都需要辨别。

已能对应的民宿优先核对准确名称、地址、建筑外观、房型与窗景。当前已打开并查看岚川携程相册中的客房参考；这不代表全部照片已归属到现有模型。听岚、梵净山舍等有公开资料入口，后续按建筑逐项核对，避免混合新旧房型。晚晴集、既山川隐世在项目旧记录中仍有位置缺口，未核实前不把它们作为精确实景落位。

参考照片用于研究；运行时使用制作出的资产，直接使用外部模型、纹理或照片时核对相应许可。网络受限只阻塞对应来源，不降低已经确定的空间完成度。

## 9 建筑与室内完整制作

每个建筑以“场地和入口—外壳—空间组织—家具与灯光—窗外关系”为整体完成。已有建筑轮廓可作为初稿，不能预先限制后续必须迁就错误窗位、层高或房间尺寸。

| 资料情况 | 设计方式 |
| --- | --- |
| 建筑与房型有明确照片 | 尽量还原门窗、布局、主要家具、材料和特色陈设 |
| 仅有部分照片 | 已知部分按资料制作，缺失部分根据外壳和功能完整补全 |
| 无对应照片 | 参考当地材料、建筑用途和生活方式完成原创设计 |

客房包括合理的睡眠、收纳、休息与卫浴关系；公共楼包含接待、餐饮、厨房及必要服务空间。家具尺度、门扇开启、通行空间、台阶与窗位应互相兼容。

细节优先顺序是空间比例与功能、主要家具与材料、采光与灯具、软装与生活细节。床品和窗帘有可信厚度与褶皱，家具接地、材质有差异，墙面和天花有合理收口；装饰数量不能代替设计。

建筑外壳、中庭或露台、室内与窗景共用坐标。不能为拍一张室内图挪动室外山体，不能用不对应的窗景贴图替代实际世界。现代民宿与传统牧居建筑分别研究，避免所有房间套同一种酒店模板。

所有确定可进入的建筑均有完整室内交付要求；非进入性附属构筑物也要有合理门窗与内部可见关系。按建筑族复用合格构件，但保留不同用途和区域的变化。

## 10 角色 物理与交互

推荐引入 Rapier 3D，使用胶囊角色控制与形状查询承接移动、滑动、台阶、坡度、落地和顶头，替代当前主要依赖终点推离的路径。Rapier 的控制器支持沿轨迹的障碍处理、台阶和坡面规则，但仍需按本项目角色尺寸和动画调校，接入库不等于已解决所有穿透。[官方角色控制器说明](https://rapier.rs/docs/user_guides/javascript/character_controller/)

静态地形使用分块高度场或简化网格，建筑使用静态网格与组合形状。门、动物等活动对象同步到统一物理状态，碰撞数据与视觉资产同时更新。

相机使用带体积的查询；平滑之后的实际位置仍须满足障碍约束。角色身体碰撞、脚部落地和动画姿态分别处理，避免只修移动路径却让坐姿或肢体持续穿模。

普通探索镜头保持合理的场景约束。明确的开发自由飞行可保留穿透能力，但与正常体验区分，不把它当碰撞验收路径。

细草可以拨开，灌木根据类型软性阻挡，树干、墙、岩石和地板承担对应实体属性。碰撞表示独立于渲染 LOD，远近切换不改变可走性。

## 11 大世界加载与性能

### 11.1 分区策略

世界数据按空间组织，地形、植被、建筑外壳、室内和物理活动范围可以使用不同粒度。沿用约 256 米分块作为室外资产起始实验值，依据场景密度与移动实测调整，不把它写死为所有系统的统一网格。

依据相机位置、视向和移动速度预取，飞行比步行提前加载。近场物理覆盖必须先于角色到达；资源未准备好时保持有效地面与障碍，不能让角色落空。

建筑外壳保持可见，接近入口或可透窗观察时加载室内。不能把所有关门房间直接判为不可见，也不能进入门口才突然补出家具或切换光照。房间可见性与外壳遮挡按真实开口处理。

门状态、交互状态和对象身份不依赖渲染分区是否被卸载。纹理、材质和几何按引用计数释放，避免长距离漫游内存只增不减。

### 11.2 将静态工作前移

图卡捕获、植物覆盖统计、静态碰撞和资产包围体在构建阶段完成。解析、解码与必要数据整理可放入 Worker；GPU 上传和场景接入分帧安排。

空间块先做可见性与距离筛选，再提交实例。不能仅依靠实例化和顶点着色器中的丢弃，就认为大量候选没有成本。

### 11.3 性能目标与验证口径

首要目标是用户实际使用的桌面浏览器。阶段 0 记录设备、浏览器、窗口尺寸、有效像素比、起始加载量和基线帧时间；默认以 1080p 级别输出、60 FPS 对应约 16.7 ms 的帧预算作为工程目标，最终验收阈值在设备实测后明确。

这是拟定目标，不是当前成绩。若质量与目标设备发生矛盾，先调整可见性、资源组织、反射阴影更新与高成本实现；不能未经讨论把整体质量或流畅度标准下调。较低帧率的高画质档可以作为可选模式，不能自动替代默认体验验收。

分别记录首个可交互画面、完整近场准备时间、静止与移动帧时间、P95/P99 长帧、峰值内存、跨区加载和多次往返后的资源回收。测试必须注明设备、分辨率、光照、机位与路线；历史 HUD 的 18–21 FPS 不作为此拷贝版本的基准。

## 12 实施顺序与阶段交付

阶段推进以可审阅结果为界。世界资料、代表资产与运行系统可在约定接口后并行，最终由同一完整版本整合；不按零碎命令或单个模型完成次数计算进度。

| 阶段 | 主要工作 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 0 范围与基线 | 核对全域、年代选择、可达性、现有资料与目标设备；记录代表视角及长路线 | 世界范围和选定内容初稿、现状画面与性能基线、未决资料清单 | 明确完整交付范围，旧入口和用户工作不受影响 |
| 1 世界骨架与接口 | 核对地形、路网、水系和聚落；统一坐标、ID、最终场景高度、资产协议与分区接口 | 全域可巡视的空间初稿、统一世界数据和加载骨架 | 主要路线贯通、地方空间关系可信，无全域结构冲突 |
| 2 共同表现与基础物理 | 统一材质、太阳天空、曝光、阴影和房间环境；接入角色与相机控制；完成一组代表材料 | 正午与暮色均成立的渲染基础、可靠的门槛坡面与落地演示 | 共享问题在系统层解决，原有主要交互可继续迁移 |
| 3 代表路线与制作流程 | 完成草甸、林缘、溪岸、岩石和一个完整建筑组；验证风动、同源 LOD、预取和室内外 | 可连续走完和飞越的高质量样区、可复用资产族与构建流程 | 所有关键系统共同成立，方法能在第二处不同地形复用 |
| 4 全域推广 | 按生态区和建筑族覆盖全部范围，补齐所有约定室内，统一远景与场地连接 | 整个约定世界达到共同基础质量，无遗留占位区域 | 跨区路线、各建筑类型及昼夜覆盖通过，样区之外同样完整 |
| 5 整体艺术与体验收尾 | 修正全景构图、重复感、区域变化和剩余穿帮；完成性能与资源回收优化 | 完整候选版本及整体验证结果 | 地方辨识度、美术统一、连续探索和性能达到约定标准 |
| 6 采用与交付 | 整理运行和制作说明，验证正式入口，按采用授权切换 | 可运行世界、可编辑源资产、可复现构建和保留的旧版本 | 用户真实入口验证完成，未完成事项明确，不将候选冒充正式采用 |

阶段 1 在全域先建立正确结构；阶段 2 与 3 只制作足以验证系统的代表资产。阶段 3 达标后推进阶段 4，不持续把第一间房或第一条溪流精修成独立作品。

阶段 4 按“生态区域加所含建筑”交付，例如一个草坡与村舍组应同时包含入口、路径、近中远植被和可进入空间，避免先做完全世界外壳却长期留下空室内。同类共享资产可批量制作。

### 12.1 实施中的第一批具体任务

下一次进入实施时，先完成以下连续工作包：

1. 确认本目录中的代码与数据为重构工作对象，建立独立的候选入口和资产目录，保留现有入口；不擅自操作其他目录中的服务。
2. 核对影像与高程来源，生成全域布局初稿，标出选定民宿、历史聚落、主要路径和可探索范围。
3. 固定一组涵盖全域的观察位置及连续路线，记录正午、低太阳、暮色与夜间画面及设备性能。
4. 建立世界坐标、稳定对象 ID、场景高度查询和环境状态接口，选取木材、石头、白布、草叶与水作为材质校准对象。
5. 建立一个从门外台阶走入室内、再望向远山的最小贯通场景，开始检验新渲染与物理接口；其任务是暴露跨系统问题，不在这一步完成整栋精装修。
6. 回到全域检查接口与表现是否可推广，然后按阶段 2 和 3 扩展。

此工作包的完成只代表重构基础开始成立，不能称整个世界完成。

## 13 整体验收

### 13.1 固定观察与连续路线

选择约 6–8 个全域观察位置，覆盖高处全景、开阔坡面、谷地、林缘、溪岸、聚落和室内窗景。位置以地方特征和跨系统风险选择，不只选择最容易出漂亮截图的机位。

主要路线为：

**远处高空眺望 → 下降到草坡 → 沿牧道进入林缘 → 林中与溪岸 → 民宿院落及台阶 → 开门进入客房与公共区 → 从窗户看回室外 → 前往另一类生态区 → 飞行跨越多个分区并返回。**

路线至少覆盖高太阳、低太阳、暮色与夜间。另做阴天、阵风、停风和必要的加载压力检查。场景亮点可以不同，但每个时段都要有可信的画面。

### 13.2 完成标准

| 维度 | 验收内容 |
| --- | --- |
| 地方辨识度 | 山脊、谷地、林带与聚落关系能支持“这里就是喀拉峻与琼库什台”的判断 |
| 时间融合 | 历史布局与选中现代内容自然共存，无重复建筑或与场地冲突的设施 |
| 地形连续性 | 近远轮廓、坡面材料与水岸连续，无因靠近而改变地貌类型的明显现象 |
| 光照 | 正午仍可读出细节，林下有层次，暮色灯光影响周围，水反光随环境与视角变化 |
| 动态 | 花头有重量，草叶有柔性，不同植物有区别；LOD 交接不重置主要运动 |
| 建筑与室内 | 所有约定可进入建筑完整，有合理功能、材质、家具和采光；入口与窗景对应室外 |
| 物理与交互 | 门洞、屋檐、台阶、坡面、落地、动态门与相机转角均可靠；检查不同帧率条件 |
| 分区与加载 | 步行、飞行和往返无明显空洞、换物、状态丢失或持续内存增长 |
| 全域美术 | 样区外达到共同质量，区域有差异，重复感受控，远景与近景属于同一个世界 |
| 可维护性 | 源工程、世界数据、派生产物关系清楚，代表资产能重新构建并在运行时得到一致结果 |

用少量有针对性的自动检查验证坐标转换、稳定 ID、LOD 对应、资产依赖、碰撞回归和构建；视觉、运动和探索体验通过实际浏览器路线验证。测试通过、离线渲染漂亮或单个样区完成，都不能替代整体验收。

每轮交付至少包含全景、行走中景、近景和室内外连续体验。发现共性问题时修正共享系统，避免对每个资产逐个增加补偿。

## 14 迁移控制 风险与投入

### 14.1 保护现有工作

本次只新增方案文档。实施时在当前复制项目内增量建立新入口和新资产版本，不覆盖旧入口或删除源文件。无需为了重构自行创建 Git 分支、worktree、提交或推送。

现有项目目前未识别为 Git 仓库，因此恢复策略不能依赖不存在的提交历史。实际改动前确认原文件与副本关系，保留受影响文件的可用旧版本和运行方式。切换正式使用入口属于独立采用步骤，不以样区通过自动代替。

旧入口只用于对照和恢复；新系统统一后，不永久维护两套相互叠加的光照、碰撞和植物分布。迁移顺序由统一接口逐步接管职责。

### 14.2 主要风险及处理

| 风险 | 处理 |
| --- | --- |
| 资料精度不足或建筑照片混淆 | 交叉检查位置、时期、房型和窗景；不确定部分明确设计补全 |
| 精细资产进入网页后仍显粗糙 | 先打通材质与光照协议，再批量制作；以实际场景回看为准 |
| 一处好看、换时段或机位失效 | 固定正午至夜间以及靠近、远离、绕看检查 |
| 一栋建筑吸走全部时间 | 达到类别标准即推广；完整世界覆盖优先于继续添加低收益装饰 |
| 渲染改造影响风、阴影和物理 | 共用空间和形变接口，迁移时验证主通道、阴影和碰撞一致性 |
| 全域精细化导致加载与内存恶化 | 分区、同源 LOD、离线构建、预取及释放同步实施 |
| 写实材料使梦幻感减弱 | 在正确受光基础上调整形状、色彩、构图和气氛，不恢复破坏层次的亮度补丁 |
| 引入成熟物理库后仍穿透 | 按角色尺度、台阶、门洞、相机和动态对象调校，验证具体失败路径 |

主要投入集中在全域地形与景观校核、自然环境资产族、完整建筑室内、统一渲染与连续世界集成。搜索和代码生成只能减少其中部分重复工作，审美迭代与真实使用验证仍是核心投入。

目前不以缺乏依据的固定天数或费用承诺排期。阶段 0 确认范围与资料，阶段 3 得到代表区域的实际制作吞吐后，按区域数量、建筑族与室内复杂度给出剩余工期区间。外部付费资产或计费生成在明确必要性和费用后另行决定，不作为启动重构的前提。

### 15.2 实施前需要确认的事实

全域地形尚未完成独立地理真值核验；现有代码中的过渡和运动问题尚未逐一做隔离运行测试；正午发白各因素的实际贡献、当前复制版本的 GPU/CPU 瓶颈、目标设备资源预算仍需实测。

这些未知项在阶段 0 至 3 内完成核实，不阻止先确定统一架构，也不能被当作已经通过的基础。完整成果的判断始终回到两个问题：熟悉这里的人能否认出这个地方，以及使用者能否在连续探索中感受到它的美好。
